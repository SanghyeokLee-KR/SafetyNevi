# 부하 측정 기록

공개 읽기 경로에 부하를 걸어 어디서 응답이 무너지는지 확인한 기록입니다. 최대 처리량을 자랑하려는 것이 아니라 병목 지점을 특정하는 것이 목적입니다.

## 측정 환경

| 항목 | 값 |
| :--- | :--- |
| 대상 | 로컬 단일 인스턴스, H2 인메모리 프로파일 |
| 실행 | `./gradlew bootRun --args='--spring.profiles.active=h2'` |
| 부하 도구 | k6 (Docker `grafana/k6`) |
| 시나리오 | VU 1에서 60까지 램프업, 총 1분 50초 |
| 대상 경로 | 시설 조회(bbox), 안전점수, 게시글 목록, 지도 페이지 |

재현 방법은 [`k6-read-endpoints.js`](k6-read-endpoints.js) 상단 주석에 있습니다.

주의: 로컬 H2 기준이라 운영 Oracle 환경의 수치가 아닙니다. 아래 값은 애플리케이션 계층과 응답 직렬화의 상대 비교로만 읽어야 합니다.

## 1회차: 기본 설정 그대로

레이트리밋이 설계대로 동작하는지 먼저 확인했습니다.

| 항목 | 값 |
| :--- | :--- |
| 시도한 요청 | 304,276건 (2,542 req/s) |
| 200 응답 | `/api` 경로 합계 600건 |
| 429 응답 | 227,610건 |
| `/map` 페이지 | 전량 200 |

`RateLimitFilter`가 `/api/**`에만 IP당 300 req/min을 적용하고 429를 돌려줍니다(`ratelimit.api.per-minute` 기본값 300, 창 60초). 측정이 1분 50초였으므로 창 2개가 지나갔고, 통과한 `/api` 요청이 정확히 600건(300 x 2)입니다. 필터를 거치지 않는 `/map`은 영향이 없었습니다.

즉 이 회차 수치는 서버 용량이 아니라 레이트리밋의 동작 확인입니다.

## 2회차: 레이트리밋을 풀고 측정한 서버 용량

`RATELIMIT_API_PER_MINUTE`를 크게 잡아 필터를 사실상 비활성화한 뒤 다시 걸었습니다.

| 항목 | 값 |
| :--- | :--- |
| 처리량 | 491 req/s (반복 123회/s, 반복당 4요청) |
| 총 요청 | 54,056건 |
| 실패율 | 0.00% (54,056건 중 2건) |
| 전체 p95 | 234ms |
| 전체 p99 | 421ms |
| 수신 데이터 | 5.7GB, 52MB/s |

경로별로 나눠 보면 차이가 큽니다.

| 경로 | 응답 크기 | 평균 | p95 | p99 | 최대 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| `/api/facilities` (bbox) | 387KB | 135ms | 376ms | 569ms | 1.11s |
| `/map` | 33KB | 53ms | 230ms | 366ms | 873ms |
| `/api/safety-score` | 387B | 42ms | 111ms | 175ms | 341ms |
| `/api/board` | 2B | 26ms | 117ms | 188ms | 359ms |

## 읽어낸 것

**병목은 쿼리가 아니라 응답 크기입니다.** 시설 조회는 서울 전역 bbox 한 번에 387KB를 내려보냅니다. 부하가 없을 때 24ms이던 응답이 60 VU에서 p95 376ms로 늘고, 이 경로 하나가 초당 52MB 전송을 만듭니다. 나머지 세 경로는 응답이 작아 부하가 올라가도 p95가 120ms 안쪽에 머뭅니다.

**레이트리밋 기본값이 실사용에는 빡빡합니다.** 지도 화면 한 번이 시설·안전점수·게시글을 함께 호출하므로 사용자 한 명이 화면을 몇 번 옮기면 300 req/min에 닿습니다. NAT 뒤 공용 IP 환경이면 더 빨리 걸립니다.

## 3회차: 병목을 고치고 다시 측정

2회차에서 특정한 병목(응답 크기)을 두 단계로 고치고 같은 시나리오를 다시 돌렸습니다.
1회차와 2회차는 레이트리밋 확인과 병목 특정이었고, 여기서부터가 교정 결과입니다.

측정은 세 판을 한자리에서 연달아 돌렸습니다. 같은 기계, 같은 시나리오, 같은 데이터입니다.
아래 기준값은 이 자리에서 다시 잰 것이라 2회차 표(다른 시점 측정)와 숫자가 조금 다릅니다.

### 고친 것 하나: 목록에서 주소를 뺐다

시설 영역 조회는 한 번에 1,500건을 내려보내는데, 응답 바이트를 필드별로 쪼개 보니
주소가 25.2%로 가장 컸습니다. 그런데 마커를 찍는 `map-marker.js` 는 주소를 쓰지 않습니다.
주소는 마커를 눌렀을 때 `/api/facilities/detail/{id}` 가 따로 내려줍니다.

목록 전용 `FacilityMarkerDto` 를 만들어 주소를 뺐습니다. 검색 결과는 주소를 보여줘야 하므로
기존 `FacilityDto` 를 그대로 씁니다.

### 고친 것 둘: 응답 압축을 켰다

같은 모양의 JSON 객체가 1,500개 반복되므로 압축이 특히 잘 듣는 형태입니다.
`server.compression` 을 켜고 2KB 미만은 제외했습니다.

여기서 시나리오의 결함을 하나 발견했습니다. k6 는 `Accept-Encoding` 을 자동으로 붙이지
않습니다. 브라우저는 붙입니다. 헤더 없이 재면 서버 압축을 켜도 압축된 응답을 한 번도
받지 않아, 실제 사용자가 겪는 전송량과 다른 값을 재게 됩니다. 처음 돌렸을 때 압축을 켰는데
전송량이 그대로여서 알았습니다. 시나리오에 헤더를 넣고 다시 쟀습니다.

### 결과

| 항목 | 기준 | 주소 제거 | 주소 제거 + 압축 |
| :--- | ---: | ---: | ---: |
| 시설 조회 응답 | 387,454 B | 289,767 B | 55,441 B |
| 시설 조회 평균 | 208.02ms | 155.52ms | 90.78ms |
| 시설 조회 p95 | 568.63ms | 397.58ms | 215.54ms |
| 시설 조회 p99 | 1.07s | 611.38ms | 295.87ms |
| 전체 p95 | 328.81ms | 243.51ms | 149.29ms |
| 처리량 | 346.85 req/s | 423.32 req/s | 579.44 req/s |
| 총 요청 | 39,308 | 46,568 | 67,692 |
| 수신 데이터 | 4.2GB, 37MB/s | 3.8GB, 35MB/s | 1.2GB, 9.9MB/s |
| 실패율 | 0.00% | 0.02% | 0.00% |

정리하면 응답이 387KB에서 55KB로 85.7% 줄고, 시설 조회 p95 가 568.63ms에서 215.54ms로
62.1% 줄었으며, 같은 부하에서 처리량이 346.85 req/s에서 579.44 req/s로 67% 늘었습니다.
초당 전송량은 37MB에서 9.9MB로 내려갔습니다.

주소 제거만으로 응답이 25.2% 줄었고 p95 가 30.1% 내려갔습니다. 압축은 거기서 다시
전송량을 80.9% 깎았습니다. 둘 중 하나만 한다면 압축이 효과가 크지만, 압축은 CPU 를 쓰고
필드 제거는 안 씁니다. 그래서 둘 다 했습니다.

## 아직 안 한 것

- 마커 클러스터링. 1,500건 상한은 그대로라 화면에 찍히는 마커 수 자체는 줄지 않았습니다.
  줌 레벨에 따라 묶으면 브라우저 렌더링 비용도 같이 줄어듭니다.
- 레이트리밋을 경로별로 나눈다. 조회는 완화하고 쓰기만 조인다.
- 운영 Oracle 환경에서 같은 시나리오를 돌려 커넥션 풀 포화 지점을 확인한다.
  위 수치는 H2 인메모리라 DB 대기가 거의 없습니다. 이 측정이 말해주는 것은
  애플리케이션 계층과 응답 직렬화까지입니다.
